# Stage 2：RAG 全链路

> 目标：把 RAG 的每个环节讲透——为什么做、怎么做、有什么坑。这是面试问得最深的部分。

## 1. 什么是 RAG，为什么需要它

**RAG（Retrieval-Augmented Generation，检索增强生成）**：先从外部知识库检索出相关内容，再把这些内容拼进 prompt 让 LLM 生成答案。

**为什么需要**：裸 LLM 有三大缺陷，RAG 逐一解决：

| LLM 缺陷 | RAG 如何解决 |
|----------|--------------|
| 幻觉（编造） | 用真实检索到的文档约束回答 |
| 知识截止（不知道新知识） | 知识在外部库，实时可更新 |
| 无法回答私有/领域知识 | 把企业私有文档做成知识库 |

一句话：**RAG = 让模型「开卷考试」而不是「闭卷答题」。**

## 2. 完整链路

```text
① 文档解析 → ② 切分(chunking) → ③ Embedding → ④ 向量入库
                                                            ↓
用户提问 → 问题Embedding → ⑤ 检索(retrieval) → ⑥ 重排(rerank) → ⑦ 拼prompt → ⑧ 生成
```

**离线阶段（建库）**：①②③④
**在线阶段（问答）**：⑤⑥⑦⑧

下面逐环节讲。

## 3. ① 文档解析（Parsing）

把 PDF/Word/HTML 等转成纯文本。常见坑：
- PDF 分「文本型」（能直接提取）和「扫描型」（需 OCR）
- 表格、公式、代码块解析容易乱，影响后续切分质量
- 面试提一句「复杂文档（表格/图文混排）是解析难点」即可加分

## 4. ② 切分（Chunking）—— 高频考点

### 为什么要切分

- embedding 模型有**最大输入长度**限制（如 1536 token），长文档必须切
- 块太小丢失上下文、太块检索不准（粒度粗）

### 常见策略

**固定长度切分（最简单）**：按固定 token 数切，带 overlap（重叠）。

- 例：每块 512 token，重叠 50 token。overlap 是为了避免关键句被切在边界上。
- 缺点：语义单元被硬切碎

**语义切分**：按段落、标题、或 embedding 相似度找「语义边界」切分。

**父子块（Parent-Child）—— 进阶加分项**：
- 检索时用「小块」（子块，如 256 token）保证召回精度
- 生成时把小块对应的「大块」（父块，如 1024 token）喂给 LLM，保证上下文完整

面试要点：**「chunk 大小怎么选？太小太大各有什么问题？」** → 答：太小语义碎片化、召回可能缺上下文；太大检索粒度粗、噪声多、还可能超 embedding 长度；需要实验调优，常用 256~1024 token，配合 overlap 和父子块策略。

## 5. ⑤ 检索（Retrieval）

就是 Stage 1 的内容落地：用户问题 → embedding → 向量库 top-k 检索。

**关键点：top-k 怎么定** → 太小漏召回，太大噪声多；配合 rerank 时可以先多召回（如 top-50）再精排（取前 5）。

### 检索优化技巧（面试加分）

- **多路召回 + 混合检索**：向量 + BM25，RRF 融合（见 Stage 1 第 6 节）
- **Query 改写/扩展**：用户问题太口语化，先用 LLM 改写成更适合检索的形式（或生成多个变体 query）
- **HyDE（Hypothetical Document Embeddings）**：先用 LLM 生成一段「假设答案」，再用假设答案去检索（假设答案和真实文档更相似）。适合用户问题与文档措辞差异大的场景。

## 6. ⑥ 重排（Rerank）—— 高频考点

**为什么需要**：向量检索是「粗排」，只算 embedding 相似度，精度有限；rerank 用专门的交叉编码器（cross-encoder）对「问题+候选文档」逐对精算相关性，把真正相关的排前面。

**rerank 和 embedding 的本质区别（必考）**：
- embedding 是**双塔（bi-encoder）**：问题和文档分别编码成向量，再算相似度 → **快，因为文档向量可以预先算好存起来**
- rerank 是**交叉编码器（cross-encoder）**：把「问题+文档」拼一起送进模型，输出一个相关性分数 → **准，但慢，因为每对都要重新过一遍模型**

所以工程上：**先 embedding 粗召回 top-50，再用 rerank 精排取 top-5**，兼顾速度和精度。

- 代表模型：Cohere rerank、bge-reranker

面试要点：**「为什么要 rerank？bi-encoder 和 cross-encoder 区别？」** → 答：如上，一个快一个准，两级漏斗配合。

## 7. ⑦⑧ 生成（Generation）

把检索到的文档作为**上下文**拼进 prompt，让 LLM「基于上下文回答」。

典型 prompt 结构：

```text
[system] 你根据下面提供的资料回答问题，资料里没有的就说不知道，不要编造。
[user]
资料：
<文档1>
<文档2>
问题：{用户问题}
```

**常见坑**：
- 上下文太长超窗口 → 控制块数/块大小，或做摘要压缩
- 检索到的内容其实不相关（噪声）→ 模型被带偏 → 靠 rerank 和相关性阈值过滤
- 答案不忠实（不忠于文档）→ 用「根据资料回答，不知道就说不知道」约束 + 评估兜底

## 8. RAG 评估（面试加分项）

怎么知道你的 RAG 好不好？从两个维度：

| 维度 | 问题 | 指标 |
|------|------|------|
| **检索质量** | 检索到的文档里有没有答案？ | 召回率（recall@k）、命中率 |
| **生成质量** | 答案对不对、有没有编？ | 忠实度（faithfulness）、答案相关性 |

**RAGAS** 是主流开源评估框架，核心指标：
- **Faithfulness（忠实度）**：答案是否忠于检索到的文档（有没有幻觉）
- **Answer Relevancy（答案相关性）**：答案是否切题
- **Context Recall（上下文召回）**：答案所需的信息有多少被检索到了

**为什么评估难**：没有标准答案，很多指标要用 LLM 当裁判（LLM-as-judge）来打分，所以评估本身也有噪声。

面试要点：**「RAG 系统上线前怎么评估/怎么迭代？」** → 答：建一个带标准答案的小测试集，分别量化检索召回率和生成忠实度；每次改切分/检索/rerank 策略都跑一遍做对比（A/B 实验），而不是凭感觉调参。

## 9. RAG 的常见问题与进阶方案（面试展现深度）

| 问题 | 进阶方案 |
|------|----------|
| 简单问题也检索，浪费且可能引入噪声 | 先判断是否需要检索（路由） |
| 多跳问题（答案需要综合多篇文档） | 迭代检索（检索→生成→再检索） |
| 文档关系复杂、需要全局理解 | GraphRAG（把文档建成知识图谱） |
| 检索质量不稳定 | Self-RAG（让模型自我判断检索结果够不够、要不要再检索） |
| 用户问题模糊 | Query 改写 / 多轮澄清 |

这些名词能说清「解决什么问题 + 大致思路」即可，不需要会实现。

## 10. 面试高频题速查

1. **RAG 解决什么问题？** → 幻觉、知识截止、私有知识，见第 1 节
2. **RAG 完整链路？** → 解析→切分→embedding→检索→rerank→生成
3. **为什么要切分？chunk 怎么选？** → 见第 4 节
4. **overlap 有什么用？** → 防止关键信息被切在边界丢失
5. **父子块是什么？** → 小块检索、大块生成
6. **为什么要 rerank？bi/cross-encoder 区别？** → 见第 6 节
7. **HyDE 是什么？** → 用假设答案检索
8. **混合检索为什么必要？** → 向量弱于精确词匹配
9. **RAG 怎么评估？** → RAGAS，faithfulness/answer relevancy/context recall
10. **RAG 生成的答案还是不相关怎么办？** → 检查检索质量（召回）、加 rerank、加相关性阈值、prompt 约束「不知道就说不知道」
